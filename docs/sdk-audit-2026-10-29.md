# @nivaro/sdk audit — 2026-10-29

Scope: `packages/sdk` (published as `@nivaro/sdk`, 0.2.7 at the time of the audit) against the
routes registered from `api/src/routes/index.ts`. Consumers checked: `packages/shared`,
`packages/mcp`, `packages/react` (through shared), and the doc sections that generate
`sdk/README.md`.

## How it was measured

- Every `app.register(…, { prefix })` in `api/src/routes/index.ts` was resolved to its route
  file, and every `get/post/put/patch/delete` inside the registering function was extracted.
  Nested sub-plugins (`infrastructure-ai`, `ai-design-layouts`, …) are not followed by the
  extractor; their SDK paths were checked by hand. Result: **2,233 routes in 254 prefix groups**.
- Every `cmd('METHOD', '/path')` in `packages/sdk/src` (plus the client's raw fetches: upload,
  import parse, GraphQL) was matched to a route by method and path shape.
- Before this change: **702 / 2,233 routes** reached by an SDK command (736 call sites);
  groups 44 covered, 81 partly, 129 missing.
- After: **770 / 2,233 routes** (806 call sites, 70 new commands); groups 52 covered, 80 partly,
  122 missing.
- 11 SDK paths did not match an extracted route; all 11 exist (nested plugin registrations or a
  multi-line generic the extractor missed). **No command calls a path that no longer exists.**
  The stale things were the realtime socket protocol, missing params and wrong result types
  (below).

Classes:

- **public**: data and workflow surfaces an external developer or the MCP server needs.
- **admin-config**: schema and configuration editors. Add when someone asks; lower priority.
- **system**: protocol endpoints driven by something other than an SDK call (SCIM, OAuth, bot
  webhooks, web push, partner webhooks).
- **ops-internal**: operator tooling that stays out of the SDK (see "Kept out").

## Fixes to existing code (provably wrong against the current API)

1. **Realtime client did not work.** `realtime.ts` emitted `subscribe` / `unsubscribe` and
   listened for `items:create|update|delete` and `notification`. The server handles none of
   these. It wants `auth {token}`, answers `auth:ok`, and takes `collection:join` /
   `collection:leave`. It sends `collection:update`, coalesced as `{ items, many, count }` under
   load, and `notification:new`. The token passed in the handshake `auth` was ignored, so every
   SDK socket stayed signed out and was dropped after `SOCKET_AUTH_TIMEOUT_MS`. Rewritten against
   `plugins/socketio.ts` + `services/realtime.ts`, keeping the public API (`connect`,
   `subscribe`, `onConnect`, `onDisconnect`, `connected`).
   - Callbacks now get `RealtimeChange[]` (`collection`, `item`, `action`, `changed_fields`).
   - `connect` also takes a token getter, which is asked on every reconnect (ws-tokens are
     single-use).
   - New: `onAuthenticated` and `authenticated`.
   - New exports: `NOTIFICATIONS_CHANNEL` and `parseRealtimeChanges`.
2. **`readRevisions` result type** was `ListResponse<Revision>`, but the route answers
   `{ data }` only (no total, limit or offset). It is now `{ data: Revision[] }`.
3. **`Revision` type** said `id: number`, `user`, and only three actions. The API sends `id` as
   null for folded pipeline and O2M entries, names the person `user_id`, and adds `comment`,
   `parent`, `via_agent` and `event`. Fixed. `user` is kept as optional and `@deprecated`.
4. **`ActivityEntry` / `ActivityQuery.action`** only allowed create/update/delete/login. The log
   holds any action (`export`, `trash-purge`, …). The type was widened and the joined fields the
   route returns were added (`ip`, `comment`, `origin`, names, `via_agent`, `user_agent`).
5. **Error message for Fastify-shaped errors.** Fastify's own errors answer
   `{ statusCode, error: 'Service Unavailable', message, code }`, and the client used `error`, so
   the 503 SERVER_BUSY and validation errors read "Service Unavailable" / "Bad Request". The
   client now uses `message` when the body has both `statusCode` and `message`. Route-handler
   `{ error }` bodies are unchanged.
6. **`globalSearch` result type** lacked `people`, `exact`, `suggestions`, `query`, `semantic`,
   `extra` and `commands`, and the `labels` param. All are now optional fields or options.
7. **`NotificationItem` / `NotificationPage`** lacked `archived`, `ack`, `sender`, `sender_name`,
   `snoozed_until`, `revision_id`, `url` and `pinned`. Added as optional.
8. **`ListResponse`** gains the optional `total_approx`, `total_timed_out`, `limit_capped` and
   `applied_limit` the list route sends.
9. **Docs**: these are fixed in the `sdk-core` / `sdk-extended` sections.
   - Commands that do not exist: `readNotifications`, `readNotificationCount` (badge),
     `bulkCreateItems`, `readPresence`, `readAllPresence`, `rt.presence.*`.
   - Wrong params: a `workspace` client option that never existed, `readRevisions(…, { limit })`,
     `readActivity({ user_id })` (the param is `user`).
   - The index.ts header showed `nivaro.realtime.connect(...)`, which the client has never had.
     Fixed there too.

Not changed, but wrong: `ListResponse.total` is typed `number`, while `count: false` and a
count timeout answer `null`. Widening it to `number | null` would break callers that do
arithmetic on it, so it is left for the next major version.

## Error handling (after)

- **`NivaroError`** (`extends Error`, `name: 'NivaroError'`) on every non-2xx from `request`,
  `graphql`, `upload` and `importParse`. Fields: `status`, `code` (`body.code`), `requestId`
  (`x-nivaro-request-id`), `response` (parsed body), `method`, `path`, `retryAfterMs` and
  `issues` (import parse).
- `status`, `response` and `issues` are where earlier versions put them, so existing
  `catch (e) { e.status }` code and shared's `err.response` readers keep working.
  `isNivaroError()` also recognises a NivaroError from a second bundled copy of the SDK.
- A GET past `timeoutMs` still throws `TimeoutError`. A caller abort (`withSignal`) still
  throws the platform `AbortError`.
- GraphQL `errors[]` still throw a plain Error with `graphqlErrors` / `extensions`, now with
  `requestId` as well.

## Retries, timeouts, abort

- Timeouts: `timeoutMs` (GET only) was already there. Each retry gets the full budget.
- Abort: `withSignal(command, signal)` was already there. It also cancels a pending retry wait.
- **Retries (new, opt-in):** `retry: n | { retries, methods, statuses, baseDelayMs, maxDelayMs }`.
  - Default methods: GET only. Default statuses: 408, 429, 502, 503, 504, plus network errors.
  - Timeouts and aborts are never retried.
  - `Retry-After` is honoured, capped at `maxDelayMs`; otherwise exponential backoff with
    jitter.
  - Writes are only retried if the caller lists their method. Most writes are not idempotent;
    use `Idempotency-Key` through `headers` / `onRequest` if you do.

## Auth modes

| Mode | SDK support |
|---|---|
| Static user token | `token` → `Authorization: Bearer`. A socket can take it directly. |
| Named API key `nvk_` | `token`. A socket needs a ws-token (`readWsToken()`); the socket `auth` handler takes only ws-tokens, View-as tokens and static tokens. |
| Session cookie | No token; `credentials: 'include'` by default. A socket needs a ws-token. |
| View-as `nvm_` | `token`. A socket can take it directly. |
| OAuth `nvo_` | `token`, but accepted only on `/api/mcp` and its in-process tool calls. Every other route refuses it, by design (gotchas: "OAuth access tokens are MCP-only"). |

There is no SDK sign-in flow (`/auth/login/password`, `/auth/login/token`, OIDC/SAML
redirects): these set a session cookie, and a browser does them as navigations. `logout`,
`logoutAll` and `readAuthProviders` were added.

## Logging and observability

Client side (new, all opt-in, nothing changes when unset):

- `onRequest(info)`: method, path, url, attempt, kind. The `headers` are mutable (tracing,
  `x-nivaro-app`, `x-workspace`). A throw fails the request.
- `onResponse(info)`: status, ok, `requestId`, `durationMs`, attempt, `willRetry`. Called for
  every attempt; it never fails the request.
- `onError(err, where)`: called once per final failure. A caller abort is not reported.
- `debug: true | fn`: one line per request (method, path, status, ms, request id). It never logs
  headers or bodies.
- `headers`: static extra headers or a function.
- Request id: the API stamps `x-nivaro-request-id` on every traced answer. It appears on
  `onResponse` and `NivaroError.requestId`.

## Kept out, and why

- `/chaos/*`: fault injection, gated by `CHAOS_ENABLED` and chaos operators. A typed client
  makes misuse easier, and there is no external use. (`chaos.ts` keeps its one `what-if` read
  for the MCP tool.)
- `/infrastructure/*`, `/ops-*`, `/db-tuning`, `/sql-checks`, `/index-advisor`, `/telemetry`,
  `/environments`, `/release`, `/runbooks`, `/quality-checks`, `/cache-config`, `/monitors`,
  `/command-center`: host, Docker, database and deploy internals. They are off in cloud mode,
  and their shapes change with the ops console. The MCP server reaches the safe summaries
  through `infrastructure-summary.ts`.
- `/traffic-map/*` (beyond the one snapshot read), `/rum`, `/session-recordings`,
  `/session-replay-*`, `/journeys`: live ops map and browser capture, fed by the apps' own
  beacons.
- `/realtime/*`, `/events`, `/stream`: socket and SSE plumbing (verification, worker script,
  replay). The SDK speaks the socket protocol itself.
- `/config-diff`, `/config-seeds`, `/config-health`, `/config-review`, `/config-conformance`,
  `/backups`, `/lineage`, `/provenance*`, `/automation-tests`, `/integration-*`,
  `/partner-dependencies`: admin consoles with UI-shaped answers.
- `/scim/v2`, `/oauth`, `/teams`, `/inbound`, `/push`, `/chat-push`, `/setup`: standard
  protocols or webhook targets with their own clients.
- `/internal/render/*`, `/widgets-internal`, `/test-data`, `/dev`: process-to-process or dev
  only.

MCP:

  fields })`, `rehearseUpdateItem`, `checkItemFilter` and `readChanges`. The shapes are the
  same.

API side (not SDK changes):

- **CORS does not expose `x-nivaro-request-id`** (no `exposedHeaders`), so a cross-origin
  browser caller cannot read it. Same-origin and Node callers can. Add it to the CORS config.
- The server does not accept a caller-supplied request id; it always mints its own. A
  `traceparent` / `x-request-id` passthrough would join a caller's trace to the server's.
- The request log stores `request_id` (migration 389), but `/api-analytics/requests` neither
  returns it nor filters by it. A `request_id` filter would let `NivaroError.requestId` be
  looked up in one call.
- `/activity` has no date-range filter, and `/revisions` has no paging (it is capped at 100).

- efp-new pins an older `@nivaro/sdk`. It does not use `createRealtime`, so the protocol fix does
  not affect it. Bump it with the next react release.
